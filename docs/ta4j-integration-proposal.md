# Предложение по интеграции ta4j в Centaur

Подготовлено 13 октября 2026 года для согласования; ниже отражён текущий срез реализации. ATR(28), EMA(20/50), RSI(14), rolling High/Low(50) и confirmed swings подключены к конвейеру.

## Что фактически есть в репозитории

- `IndicatorAnalyzer` объявляет `void analyze(MarketContext context)`. `MarketContext` содержит `InstrumentSnapshot`, один `BarSeries` и `EnumMap<MetricName, TechMetrics>`.
- Прежние `EmaAnalyzer` и `AtrAnalyzer` **не реализовывали** `IndicatorAnalyzer`, не вызывались из общего вычислительного конвейера и принимали `List<ru.sewaiper.derivative.analyst.domain.tinvest.candles.Candle>` напрямую. Их самописные математические циклы удалены перед переходом на ta4j.
- `AtrMetrics` и `EmaMetrics` реализуют `TechMetrics` и хранят значения ta4j `Num`.
- API-DTO `Candle` имеет `time`, OHLCV и `isComplete`. `TInvestMarketDataProvider` отбирает последние 200 закрытых свечей; `TInvestCandleData` хранит их исходные `Quotation` и timeframe внутри `InstrumentSnapshot`. `MarketCandle`, `CandleEntity` и `CandleDao` удалены. Выбранные свечи сохраняются в `market_snapshots` до создания `BarSeries`.
- В `build.gradle` используется `ta4j-core:0.22.6`, совместимый с текущей Java 21.
- `IndicatorAnalysisService` создаёт один `MarketContext` с `BarSeries` и последовательно вызывает зарегистрированные `IndicatorAnalyzer`. `AtrAnalyzer` рассчитывает ATR(28), `EmaAnalyzer` — EMA(20/50) и производные величины, `RsiAnalyzer` — RSI(14) и его изменение; результаты попадают в карту метрик.

Это важно для оценки объёма: предложение «сохранить концепцию анализаторов» означает довести её до рабочего состояния, а не лишь заменить формулы в уже подключённых реализациях.

## API ta4j и построение серии

По локальному JAR проверены `BaseBarSeriesBuilder`, `series.barBuilder()` и индикаторы. `BarSeries` можно создать один раз, задав `NumFactory`, затем добавлять бары через `barBuilder().timePeriod(...).beginTime(...).endTime(...).openPrice(...).highPrice(...).lowPrice(...).closePrice(...).volume(...).add()`. Для последнего значения использовать `series.getEndIndex()`. EMA: `new EMAIndicator(new ClosePriceIndicator(series), period)`, ATR: `new ATRIndicator(series, period)`, RSI: `new RSIIndicator(new ClosePriceIndicator(series), period)`.

В этой версии `EMAIndicator`, `ATRIndicator` и `RSIIndicator` возвращают `NaN` на начальных индексах до окончания нестабильного периода: для периода `n` нужен как минимум `n+1` бар при индексации с нуля. Это отличалось от удалённой реализации EMA, где расчёт стартовал с SMA первых `n` закрытий, и может изменить значения даже после прогрева. ATR использует Wilder/MMA. Период, warm-up, `NumFactory`/точность, библиотечная версия и правило округления должны входить в версию расчёта. Не считать любое finite значение гарантией достаточной истории для стабильного исследования: минимальную длину окна и политику warm-up нужно определить отдельно.

По умолчанию `BaseBarSeriesBuilder` использует `DecimalNumFactory`; можно явно зафиксировать `MathContext` на уровне серии. `DoubleNumFactory` доступен, но выбор точности влияет на результаты. Глобальную настройку точности ta4j лучше не использовать.

`BarSeries` и `Bar` изменяемы: доступны добавление и замена баров, а также ограничение максимальной длины серии. `getBarData()` копирует список, но не сами бары. **Уточнённое решение владельца: сохранять только свечи, фактически использованные в расчёте или проверке гипотезы, а `BarSeries` не сериализовать.** Для каждого анализа создаётся локальная серия из отобранных данных, используется для вычислений и затем освобождается. В ta4j бар содержит начало и конец периода, `Duration`, OHLCV, amount и число сделок; признаки источника и завершённости свечи надо проверять до построения серии.

## Рекомендуемый минимальный поток данных

```text
T-Invest Candle DTO
  → отбор пригодных свечей и неизменяемая запись использованных значений
  → SQLite market_snapshots: точные DTO свечей и timeframe
  → один BarSeries на запуск анализа после сохранения снимка
  → EmaAnalyzer / AtrAnalyzer через общий MarketContext
  → EmaMetrics / AtrMetrics в карте TechMetrics
```

1. **Согласовано с владельцем:** DTO провайдера сначала сохраняются как `TInvestCandleData`, затем переводятся в `BarSeries`. Собственный `MarketCandle` и старые реализации индикаторов не сохраняются ради совместимости. ta4j — основной формат свечей во время расчёта.
2. Перед расчётом проверить порядок, уникальность времени, timeframe, границу доступности данных, завершённость и OHLC. Сохранить последние ровно 200 закрытых свечей, использованных для индикаторов, с UID контракта, interval, границами запросов, временем получения, количеством отброшенных свечей и причиной отбора. При отложенной оценке сохранить выбранную целевую закрытую свечу, использованную для сравнения с прогнозным диапазоном. Не хранить неиспользованный хвост ответа API. Котировку и стакан хранить в объёме использованных значений; полный запрос/ответ Gemini сохранять. Пронести выбранный timeframe в context и построить **один** `BarSeries` для обоих анализаторов. Не строить серию в каждом анализаторе и не добавлять отдельную иерархию адаптеров/фабрик. Серию не передавать в долговременное хранилище.
3. `AtrAnalyzer`, `EmaAnalyzer` и `RsiAnalyzer` реализуют `IndicatorAnalyzer`, используют ta4j напрямую и записывают вычисленные метрики через `context.addMetric`. Интерпретация, текст и гипотезы остаются вне анализаторов.
4. Позже добавить `RsiAnalyzer` тем же способом; rolling/pivot-геометрию решать отдельно. Не подключать стратегии, ордера и торговые механизмы ta4j.

Переход свечей один: DTO провайдера в `BarSeries`. Данные `isComplete`, идентификатор контракта, timeframe, источник и времена наблюдения не выражаются самим баром ta4j; они используются при проверке входа и в метаданных наблюдения. Привязка к ta4j принята осознанно. Сохраняются выбранные входные свечи, индикаторы и факты, переданные Gemini, с параметрами расчёта. Это позволяет повторно построить серию из **тех же использованных значений**, даже если API позднее вернёт другие данные. Неиспользованная часть ответа не воспроизводится; в журнале фиксируются правила фильтрации и количество исключённых свечей. Сохранённые значения нельзя обновлять на месте; новый запуск создаёт новую запись.

## Узкие решения и проверка

1. **Согласовано — граница свечной модели:** `InstrumentSnapshot` хранит `CandleData`; реализация T-Invest содержит `serialize()`, статический `restore()` и `toBarSeries()`. `MarketCandle` удалён. Дополнительных слоёв для замены ta4j нет.
2. **Согласовано — числовая совместимость:** библиотечные определения ta4j становятся новыми версионированными результатами; старые SMA-seed и округление не повторяются.
3. **Согласовано — хранение:** в БД сохраняются только свечи, участвовавшие в расчёте или проверке. `BarSeries` не сериализуется; при повторном расчёте серия заново строится из сохранённых входных значений.
4. **Согласовано — точность:** использовать `DecimalNum` и типы `Num` ta4j в вычислительных метриках вместо `double`. Конкретный `MathContext` фиксируется в версии расчёта; при сохранении чисел и передаче Gemini не терять десятичную точность. Способ сериализации `Num` в журнал ещё уточняется.
5. **Согласовано — достаточность истории:** для первого среза отбирать последние **ровно 200 завершённых** свечей в корректном временном порядке перед расчётом EMA/ATR. Если их меньше, метрики недоступны с явной причиной; не передавать ноль/NaN в Gemini как результат.

Анализ запускается только по HTTP-запросу пользователя. `POST` сразу возвращает ID анализа; `GET` по ID выдаёт статус, объяснение Gemini, три `MarketHypothesis` типа `TERMINAL_PRICE_RANGE` на 1, 5 и 10 торговых дней MOEX и позднее их оценки. Java отсчитывает горизонты от времени фиксации снимка, считая следующий торговый день первым, и до обращения к Gemini фиксирует три целевых момента по расписанию MOEX. Целевой момент — конец основной сессии соответствующего дня; для оценки берётся первая свеча выбранного timeframe, относящаяся к этой торговой сессии и закрывшаяся не раньше целевого момента. Если серия истекает до десятого торгового дня, запуск отклоняется до Gemini. Один вызов модели должен вернуть три прогноза; конкретные промпт и JSON-контракт — следующая итерация. На следующий календарный день после каждой целевой сессии задачи `db-scheduler` сравнивают `close` её свечи с соответствующим диапазоном. Для каждого запуска нужен постоянный журнал шагов с входами, выходами, временем и итоговыми ошибками: запросы API и ответы, фильтрация свечей, расчёт индикаторов, обращение к Gemini и фиксация результата. Temporal решено не добавлять. Отдельную политику длительного простоя приложения в первом MVP не проектировать; использовать простое штатное поведение планировщика при следующем запуске. Для HTTP 5xx и сетевых таймаутов — до трёх попыток; в БД сохраняется первый успешный ответ либо итоговая ошибка шага, без отдельных записей каждой неудачной попытки. После окончательного `FAILED` ручного возобновления того же анализа в MVP нет; новый запрос пользователя создаёт новый ID.

Эталонные тесты: известный ряд OHLC с проверенными EMA/ATR, плоский и гэповый ряд, перестановка/дубль времени, незакрытая свеча, граница решения, длина 199 против 200 завершённых баров, отсутствие NaN в опубликованной метрике, одинаковый результат при восстановлении серии из сохранённых использованных свечей. Запуск `./gradlew test` должен оставаться без сети и токена.

EMA, ATR, RSI, rolling High/Low и confirmed swings проверяются на искусственных рядах и сохранённой выгрузке реальных свечей. Следующие индикаторы добавляются в тот же `MarketContext`.
