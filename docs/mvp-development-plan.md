# Centaur Trading: план исследовательского MVP

Обновлено 17 октября 2026 года. Основной сценарий — перспективное наблюдение за текущим рынком, без исторического backtest и без постоянного сканирования стакана. План включает уже выполненные технические шаги и оставшуюся работу.

Актуализация входа анализа: пользователь выбирает серию инструмента без таймфрейма. Система запрашивает H1 за последние 30 календарных дней и сохраняет до 120 закрытых свечей, D1 — за 150 дней и до 100 свечей. Доступные индикаторы рассчитываются отдельно для обеих серий; отсутствие одной серии не отменяет анализ, отсутствие обеих завершает запуск до запроса Gemini.

## Цель и границы

Пользователь вручную выбирает конкретную серию фьючерса MOEX и запускает анализ через HTTP. `POST` сразу возвращает ID, а `GET` по ID — статус и затем объяснение Gemini с тремя гипотезами `TERMINAL_PRICE_RANGE` на **1, 5 и 10 торговых дней**. По ручному запуску Centaur обращается к API, сохраняет закрытые свечи H1 и D1 как неизменяемый ввод и рассчитывает индикаторы. Java от времени фиксации снимка заранее определяет три целевых момента по расписанию MOEX и правило выбора будущих закрытых свечей; Gemini получает их, но не меняет. На следующий календарный день после каждой целевой сессии фоновая задача получает относящуюся к ней закрытую свечу и сравнивает её `close` с прогнозным диапазоном. Исходные гипотезы не меняются задним числом. Цель — учиться интерпретировать рынок и копить объективную статистику, а не управлять сделками.

Нет реальных ордеров, торгового счёта, автоматического выбора активов, исторического backtest, непрерывного мониторинга стакана ради выхода из виртуальной позиции и обещаний доходности. Прошлые завершённые свечи нужны **только для расчёта индикаторов на текущий момент**. Реальный T-Invest используется только для чтения, песочница не обязательна.

## Что уже есть и чего нет

В коде есть T-Invest-клиент для справочника, свечей, рыночных значений и стакана; `InstrumentSnapshot`, SQLite/Liquibase. HTTP `POST /api/v1/analyses` записывает UUID и входные параметры в `analysis_runs`, возвращает ID и запускает `AnalysisCoordinator.prepare(...)` в отдельном пуле. `GET /api/v1/analyses/{id}` читает состояние из SQLite. Координатор получает снимок через `MarketDataProvider` (`TInvestMarketDataProvider`), сохраняет его в `market_snapshots` и только после завершения этой транзакции вызывает `IndicatorAnalysisService`. Провайдер через отдельные загрузчики для фьючерса, акции и облигации берёт паспорт, торговые параметры и `exchange` из актуальной карточки по UID, не читая локальный словарь. Отобранные закрытые свечи H1 и D1 остаются в DTO T-Invest с точными `Quotation` внутри `TInvestCandleData`; `serialize()` сохраняет их в JSON, статический `restore()` восстанавливает, `toBarSeries()` строит отдельную серию каждого таймфрейма с `DecimalNum` для `MarketContext`. Прогнозный сценарий для акций и облигаций ещё не согласован, особенно единицы цены облигаций и правила оценки. Координатор определяет торговые горизонты по `exchange` из снимка; они сохраняются в `analysis_run_horizons`. Статус `PREPARED` пока означает завершённую подготовку, а не готовый прогноз. Для фьючерсов Gemini и сохранение трёх валидированных гипотез подключены; планирование оценки ещё не реализовано. Старые самописные EMA/ATR удалены; ATR(28) и EMA(20/50) рассчитываются через ta4j. `LiquidityAnalyzer` рассчитывает показатели из сохранённого снимка стакана и ATR; `LevelAnalyzer` рассчитывает rolling High/Low(50) и confirmed swings 2/2; `MarketAnalyzer` фиксирует текущие значения провайдера и их арифметические отношения; контроллер `/api/v1/features` — заготовка. RSI(14) рассчитывается через ta4j; отложенной оценки пока нет.

В `TInvestConfiguration` устранён trust-all TLS: клиент доверяет серверному сертификату из `tbank.ru.pem` и проверяет hostname. Токен берётся из `T_INVEST_TOKEN`; HTTP 5xx и сетевые таймауты повторяются не более трёх попыток. Добавлен расчёт трёх торговых горизонтов из расписания площадки, возвращённой провайдером; пробный сетевой вызов из `main` удалён. Устаревшие `CandleDao` и `CandleEntity` удалены; историческая миграция таблицы `candles` остаётся в цепочке Liquibase для существующих БД, но новый конвейер эту таблицу не использует. Текущий снимок собирается несколькими вызовами и не является атомарным. Подробности — в `source-audit.md`.

Рассчитанные метрики уже сохраняются в `analysis_metrics` как версионированный JSON с точными десятичными строками и возвращаются через `GET /api/v1/analyses/{id}`. Журнал `analysis_steps` фиксирует вход, выход, время и ошибку шагов подготовки и Gemini; `GET /api/v1/analyses/{id}/steps` позволяет просмотреть его. Объёмные исходные свечи хранятся один раз в неизменяемом снимке, на который журнал ссылается по ID анализа.

Для фьючерса после подготовки один запрос Gemini содержит рассчитанные факты, последнюю закрытую цену и три целевых момента. Минимальный JSON-контракт требует по одному `TERMINAL_PRICE_RANGE` для дней 1, 5 и 10, границы в десятичных строках, аргументацию, альтернативный сценарий и факторы неопределённости. Java отклоняет отсутствующие или повторные горизонты, незавершённый ответ, неверные границы и цены вне шага инструмента. `llm_exchanges` сохраняет запрос, ответ, `model`, `finish_reason`, `usage`, исходный `content` и причину ошибки валидации; принятые диапазоны сохраняются в `market_hypotheses`. Всё доступно через `GET /api/v1/analyses/{id}/forecast`. Для запуска нужно задать `LLM_TOKEN` и `LLM_MODEL` (имя модели, проверенное с AITUNNEL). Сетевой тест не входит в обычный набор JUnit.

Для локальной проверки вычислений `POST /api/v1/analyses` принимает необязательное поле `skip` типа `Set<SkippableStep>`. Доступны `MARKET_TICK`, `ORDER_BOOK`, `FORECAST`; отсутствие поля или `null` означает пустой набор. Например, `{"providerId":"uid","assetType":"FUTURE","skip":["MARKET_TICK","ORDER_BOOK","FORECAST"]}` запускает сбор свечей, сохранение снимка, расчёт свечных показателей и горизонтов без текущей котировки, стакана и вызова Gemini. `MarketAnalyzer` и `LiquidityAnalyzer` пропускаются вместе со своими источниками. Выбранный набор записывается в `analysis_runs` и возвращается через `GET` по ID. Успешный запуск без прогноза завершается в `PREPARED`; запуск с прогнозом получает `FORECASTING` при сохранении метрик, затем `FORECASTED`. Обязательные шаги не имеют опции пропуска.

## Минимальная архитектура и данные

`InstrumentSpec` задаёт конкретную серию, экспирацию, тик и стоимость шага. Завершённые свечи читаются через API, сохранённые значения H1 и D1 преобразуются в отдельные `BarSeries` ta4j для расчёта; серия остаётся в памяти только на время анализа. Неизменяемая запись наблюдения содержит снимок Bid/Ask и доступных объёмов **на момент анализа**, рассчитанные Java признаки, источник и раздельные времена события/получения/решения. EMA/ATR рассчитываются при достаточной истории своего таймфрейма; расчёты используют `DecimalNum` и типы `Num` в метриках. Одно `Observation` содержит `snapshotCapturedAtUtc`, таймфреймы входных серий, версию использованного расписания MOEX, горизонты 1/5/10 торговых дней, их `targetAtUtc` и единое правило выбора целевых свечей. Для каждого горизонта своя `MarketHypothesis` с диапазоном закрытия, аргументами, альтернативой и неопределённостями; затем своя `HypothesisEvaluation` с `HIT`, `MISS` или `NOT_EVALUABLE`, фактической ценой, ошибкой и источником. Рекомендация `ALLOW_ENTRY/WAIT/NO_TRADE`, если выводится, не влияет на оценку диапазона.

Java → Gemini: один вызов со структурированными числами с единицами, параметрами, timeframe, временем доступности и источником, а также тремя определёнными Java горизонтами и целевыми моментами. Gemini не считает индикаторы и не присваивает ground truth. Точный промпт и JSON-контракт — следующая итерация; технический конвейер готовится раньше. Java должна валидировать привязку трёх `TERMINAL_PRICE_RANGE` к горизонтам и числовые границы; неоднозначный ответ отклоняется. Хранить полный запрос/ответ, причину отказа при валидации, model ID, параметры, версии prompt/schema/расчётов и hash snapshot. Диапазон не называется гарантией или откалиброванным доверительным интервалом.

| Таблица SQLite | Назначение |
|---|---|
| `instrument_specs` | UID серии, биржевой код, экспирация, единицы, тик/стоимость, источник спецификации |
| `observation_candles` | Возможное будущее раздельное хранение свечей проверки; исходные свечи H1 и D1 уже сохранены в `market_snapshot_candles` без сериализации ta4j |
| `observations` | серия, snapshot ID, `snapshotCapturedAtUtc`, таймфреймы входных серий, ссылка/версия расписания и общий технический status |
| `market_snapshots` | Сейчас: неизменяемый исходный снимок, включая DTO выбранных свечей, паспорт, котировку, стакан и торговые параметры |
| `analysis_metrics` | Сейчас: один неизменяемый набор вычисленных метрик на запуск, версия формата и расчёта, время вычисления; `Num` сохранены точными десятичными строками |
| `analysis_runs` | Сейчас: статус подготовки, выбранный `skip` и горизонты в `analysis_run_horizons`; запрос и ответ Gemini хранятся отдельно в `llm_exchanges` |
| `analysis_steps` | постоянный журнал шагов анализа с использованными входами и выходами, временем, статусом и итоговыми ошибками; лишняя часть ответов API не сохраняется |
| `market_hypotheses` | три неизменяемых `TERMINAL_PRICE_RANGE` на один запуск: горизонт, `targetAtUtc`, правило выбора свечи, нижняя/верхняя границы, аргументы, альтернатива, неопределённости |
| `hypothesis_evaluations` | отдельная оценка каждого горизонта: версия evaluator, `HIT/MISS/NOT_EVALUABLE`, фактический close, ширина диапазона, ошибка, время и источник целевой свечи |

Отдельная таблица непрерывной истории стакана **не нужна** для первого MVP. На каждом запуске анализа сохраняется использованная котировка в `market_snapshots`. При оценке через API получаются заранее определённые целевые закрытые свечи; сохраняются только их использованные значения, исходы и ошибки прогнозов. При желании можно сохранить текущий снимок котировки на горизонте, но он не подменяет `close` целевой свечи. Если позже потребуется исследовать изменение спреда, отдельно решать вопрос о периодическом сборе котировок.

## Жизненный цикл и первый срез

`CREATED → SNAPSHOT_CAPTURED → ANALYZED → AWAITING_HORIZON → COMPLETED`; `FAILED` — технический сбой. Если до вызова Gemini не удалось определить все три целевых дня либо серия истекает слишком рано, анализ прерывается без гипотез. Три горизонта оцениваются отдельно по мере наступления целевых моментов; наблюдение завершено после обработки всех трёх. `NOT_EVALUABLE` — исход оценки отдельного горизонта, когда после прогноза достоверную целевую свечу определить нельзя; остальные горизонты продолжают оцениваться. После перезапуска worker поднимает ожидающие записи из SQLite и оценивает их идемпотентно. Он **не отслеживает рынок ради открытия или закрытия позиции**. Java получает закрытые свечи по заранее сохранённому правилу; если свеча недоступна или данные сомнительны, не выбирает удобную замену задним числом.

Первый вертикальный срез: одна выбранная серия инструмента, H1 и D1, три фиксированных горизонта, три гипотезы `TERMINAL_PRICE_RANGE` из одного ручного запуска и автоматические отложенные оценки. Java сравнивает каждый диапазон с фактическим `close` своей целевой свечи. Отчёт показывает `HIT/MISS/NOT_EVALUABLE`, границы, ширину, промах и аргументы отдельно по горизонту; число запусков и число оценённых прогнозов не смешиваются. После первых 20–40 запусков критерии можно пересмотреть, сохранив версии evaluator и не смешивая статистику разных версий. Оценка «сколько бы заработали» не входит в обязательные метрики среза. Позже сравнить прогнозы Gemini с заранее определённым диапазоном на основе исторической волатильности на тех же наблюдениях.

## Этапы

1. **Аудит источника и времени:** выбрать серию MOEX; проверить свежесть свечей/котировки, timestamps, спецификацию, расписание MOEX на 10 будущих торговых дней и ограничения API. TLS исправлен, пробный вызов расписания из `main` удалён, расчёт горизонтов добавлен; остаётся проверить реальные данные выбранного контракта.
2. **Достоверные входные факты:** неизменяемая копия использованных закрытых свечей H1 и D1, отдельные `BarSeries` ta4j, EMA/ATR/RSI, уровни, текущий Bid/Ask, сохранённые признаки и тесты на отсутствие будущего. Снимок и набор метрик уже сохраняются; остаются проверки свежести и полного происхождения данных.
3. **Гипотезы:** минимальный structured Gemini response с тремя диапазонами, Java-валидация, неизменяемый запрос/ответ и три `MarketHypothesis` уже подключены для фьючерса. Остаётся проверить фактический запуск с выбранной моделью и доработать содержательный промпт отдельно от транспортного контракта.
4. **Отложенная оценка:** три оценки на `db-scheduler` на следующий календарный день после соответствующей торговой сессии, получение фактических `close`, `HIT/MISS/NOT_EVALUABLE` и возобновление после перезапуска.
5. **Обучающий отчёт:** первоначальные аргументы, фактический `close`, ширина диапазона, величина промаха, неопределённости, разрез по серии/горизонту и размер выборки.

Новые оценки времени дать после аудита. Прежний целевой win rate 55–60% относится к торговому эксперименту и не служит критерием готовности наставника.

## Открытые решения и критерии приёмки

Нужна первая конкретная серия MOEX. При недостатке истории отдельные метрики недоступны; если обе серии пусты, Gemini не вызывается. Контракт гипотезы описан в `hypothesis-rules.md`. Проверки: обычные тесты без сети/токена/рабочей БД; эталонные индикаторы; расчёт без будущих/незавершённых свечей; вычисление дней 1/5/10 из календаря; отклонение серии с экспирацией до последнего горизонта; валидация трёх диапазонов; неизменяемые факты и гипотезы; идемпотентная оценка после перезапуска; праздники и отсутствие целевой свечи.

MVP готов, когда пользователь задаёт серию, получает объяснение Gemini и три прогноза диапазонов на 1, 5 и 10 торговых дней, а после каждого целевого момента видит фактический `close`, `HIT/MISS/NOT_EVALUABLE`, ширину диапазона и величину ошибки. Реальных действий с активом система не совершает.
